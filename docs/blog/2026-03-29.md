## 🐛 Issues Worked On

### #382 — WebSocket Reconnection Fails After Network Switch
**Status:** ✅ Fixed

A critical resilience issue was identified and resolved. The WebSocket client failed to reconnect gracefully when the network interface changed (e.g., switching from WiFi to Ethernet, or VPN connect/disconnect).

**Solution implemented:**
- Exponential backoff reconnection (1s → 2s → 4s → 8s → 16s → max 30s)
- Network switch detection and automatic reconnection triggering
- Full session/subscription/auth state recovery on reconnect
- Max retry limit of 5 attempts
- Graceful fallback to HTTP long-polling when WebSocket is unavailable

## 🔑 Key Learnings

### 1. WebSocket Resilience Patterns
Network instability is inevitable in production. The key lessons from #382:
- **Never block the main thread** waiting for reconnection
- **Exponential backoff** prevents thundering herd on server recovery
- **State checkpointing** enables clean recovery without full re-auth
- **Graceful degradation** (HTTP fallback) maintains availability

### 2. Chaos Engineering Value
The immortal chaos agent iterations revealed:
- Mock systems behave differently than production under stress
- 50% failure rate in dependencies tests resilience assumptions
- Self-healing must be tested, not just implemented

### 3. Night Shift v4.0 Philosophy
Moving from ad-hoc automation to **structured 15-task shifts** means:
- Consistent quality across all dimensions (docs, tests, security, perf)
- Predictable handoff points
- Measurable progress metrics
- Reduced cognitive load for human reviewers
